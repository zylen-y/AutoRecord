# Dock-app conversion design

**Date:** 2026-06-02
**Status:** Approved
**Author:** zylenyoung@gmail.com (via Claude)

## Goal

Convert AutoRecord from a menu-bar-only "agent" app into a hybrid app that has a real Dock presence and a main window, while preserving the menu-bar extra for at-a-glance recording state.

## Motivation

The current `LSUIElement: true` configuration hides the app from the Dock and ⌘-Tab. The schedule manager exists as a secondary `Window("schedules")` that the user must open explicitly from the popover. As the app's scope grows beyond a single popover view, users expect:

- A persistent Dock icon they can click to bring the app forward.
- A main window that opens on launch.
- Standard macOS app affordances (⌘-Tab, main menu, ⌘-, settings).

We're not abandoning the menu-bar UX — the "is it recording right now?" glance is core to the product. We're adding Dock presence alongside it.

## Non-goals

- Removing or redesigning the `MenuBarExtra` popover.
- Custom main-menu commands (⌘N, custom shortcuts) — defer to SwiftUI defaults for now.
- Sidebar / `NavigationSplitView` redesign of the schedule list.
- Dock tile customization (badges, progress, custom icons during recording).
- Changes to recording, scheduling, MCP, or persistence subsystems.

## Architecture changes

### 1. Info.plist (`project.yml`)

Remove `LSUIElement: true` from `targets.AutoRecord.info.properties`. Everything else in the Info.plist stays.

**Effect:** the app becomes a regular foreground macOS app — visible in Dock, in ⌘-Tab, with a normal main menu auto-generated by SwiftUI.

### 2. Scene composition (`AutoRecordApp.swift`)

Current scenes (in order):

1. `MenuBarExtra { MenuBarPopoverView() } label: { … }` — popover.
2. `Window("AutoRecord — Schedules", id: "schedules") { ScheduleListView() … }` — secondary, opened on demand.
3. `Settings { SettingsView() … }` — standard preferences scene.

After the change:

1. `WindowGroup { ScheduleListView() … }` — **main window**, opens on launch. Uses `WindowGroup` (not `Window`) so users can ⌘N a new instance if they want, and to get the standard "reopen window" behavior from the Dock icon.
2. `MenuBarExtra { MenuBarPopoverView() } label: { … }` — unchanged.
3. `Settings { SettingsView() … }` — unchanged.

The old `Window("schedules")` is removed (its content moves into the `WindowGroup`).

### 3. Application lifecycle (`AppDelegate`)

Add a minimal `NSApplicationDelegateAdaptor` to `AutoRecordApp`:

```swift
final class AppDelegate: NSObject, NSApplicationDelegate {
    func applicationShouldTerminateAfterLastWindowClosed(_ sender: NSApplication) -> Bool {
        false
    }

    func applicationShouldHandleReopen(_ sender: NSApplication, hasVisibleWindows flag: Bool) -> Bool {
        // Returning true lets AppKit reopen / unminimize the main window.
        // SwiftUI's WindowGroup recreates the window automatically when this returns true and no windows are visible.
        true
    }
}
```

Wired via `@NSApplicationDelegateAdaptor(AppDelegate.self) var appDelegate` in `AutoRecordApp`.

**Why this matters:** without it, closing the main window quits the app, which would stop the scheduler — a regression. The reopen handler ensures clicking the Dock icon brings the window back when no windows are open.

### 4. `ScheduleListView` — inline recording banner

When the popover is the only UI surface, the main window doesn't need to show recording state. After this change, the main window will often be the only thing visible. Add a thin banner at the top of `ScheduleListView`:

- Hidden when `recorder.isRecording == false`.
- Visible when recording: shows a red dot, the current schedule title, elapsed time (`recorder.elapsedTimeString`), and a "Stop" button calling `recorder.stopAndSaveNow()`.
- Data sources are already on `recorder` (`@EnvironmentObject`); no new state.

This is the only new UI work. It mirrors data the popover already surfaces — no duplication of business logic, just a second view of the same observable state.

### 5. Popover "Open Manager…" button

In `MenuBarPopoverView`, the button currently calls `openWindow(id: "schedules")`. Give the new `WindowGroup` an explicit id — `WindowGroup(id: "main") { ScheduleListView() … }` — and update the button to call `openWindow(id: "main")` plus `NSApp.activate(ignoringOtherApps: true)` so the window comes forward even when the app is in the background. This handles both first open and re-focus through a single code path.

## Risk register

| Risk | Mitigation |
|---|---|
| First-launch window doesn't come forward (focus lost to terminal during `xcodebuild`/Xcode launch). | Verify manually after build; if needed, add `NSApp.activate(ignoringOtherApps: true)` in `applicationDidFinishLaunching`. |
| `SMAppService` login-at-login behavior changes when the app is no longer an agent (`LSUIElement: false`). | Test login-at-login flow end-to-end after change. The service should work — `SMAppService.mainApp` is documented for regular apps too — but worth verifying. |
| `WindowGroup` allows multiple windows of the same content via ⌘N. Two `ScheduleListView`s could each instantiate their own state and conflict. | `ScheduleStore` is injected via `@EnvironmentObject` from the App scene, so both windows share the same store. Safe. |
| `MenuBarExtra` behaves slightly differently when the app is not `LSUIElement` (e.g., focus stealing on popover open). | Sanity test; documented behavior is that `MenuBarExtra` works for both kinds of apps. |
| App now appears in ⌘-Tab and on first launch may steal focus from whatever the user is doing. | Acceptable for a Dock app. The user opted into this. |

## Testing

Manual end-to-end after the change:

1. `xcodegen generate && xcodebuild … build && open …/AutoRecord.app`.
2. Verify: Dock icon appears, main window opens on launch, app is in ⌘-Tab.
3. Verify: menu bar icon still present, popover still works.
4. Verify: close main window → app stays alive (menu bar icon persists, scheduled recording fires).
5. Verify: click Dock icon while main window is closed → window reopens.
6. Verify: ⌘, opens Settings; ⌘W closes the main window without quitting.
7. Verify: add a schedule starting in ~30s, close main window, confirm recording starts.
8. Verify: login-at-login toggle in Settings still works (toggle off then on, restart, confirm app launches).

Automated tests: no changes — the `swift test` suites for `AutoRecordShared` and `AutoRecordMCP` are unaffected.

## Rollout

Single PR / commit. No feature flag (no point — the change is the new default).
